Opportunity Flow — User Journey & Pain-Point Audit

Scope: the Commodity Manager's end-to-end path through an opportunity — Feed → Qualify → Decide → Act → Commit → handoff to Value Realization. Two journeys are mapped stage-by-stage: the current deployed build (allison-procurement-931u.vercel.app, "as-is") and the prototype v2.1 (the to-be reference this session produced). This is the input document for the next step — deciding, together, what the target production experience should actually be.

PART 01

How to Read This

Each stage below shows two cards side by side: As-is what a Commodity Manager actually experiences today in the deployed build, sourced from reading the live source code and pulling real data from its API — not a screenshot (headless-browser access to the hydrated deployed app is blocked in this sandbox, so the as-is column is evidenced by code + data, not pixels). To-be is prototype v2.1, illustrated with real screenshots.

This is a diagnostic, not a decision. Nothing here is a final design. The point of this document is to put the actual current friction and the prototype's proposed resolution next to each other so we can decide, stage by stage, what's worth building, what needs a different answer than the prototype gives, and what's genuinely out of scope for now (e.g. the prototype's "Mercer analyzes your evidence" is a keyword heuristic standing in for a real LLM call — that's a build decision, not a UX one, and it's flagged in §5).
PART 02

Journey Map — Stage by Stage

Both journeys are the SAME persona (Maria Vance, Commodity Manager · MRO) and the SAME task ("triage this week's sweep, decide, and move value into execution").

Stage 0 — Arrive & orient "What needs me today?"

⚠ As-is · Deployed build
GoalKnow what's changed and what deserves attention first.
What happensLands on the Command Center. A prose paragraph ("Mercer synthesis") narrates totals; five KPI tiles restate some of the same numbers. No single "what needs me" surface — the CM has to read the paragraph, scan the tiles, then click into Opportunities to actually see anything actionable.
  • No prioritized "act on this" surface — everything is narrated prose or passive KPI tiles, nothing is a queue.
  • No way to tell what's new since the last visit before opening the feed.
  • The synthesis paragraph and KPI tiles fetch independently — during a slow load they can transiently disagree (no shared loading gate).
✓ To-be · Prototype v2.1
GoalSame.
What happensAn "attention strip" of four titled, denominated cards sits above the narrative: Awaiting triage (5 of 7), Drift alerts (1 of 2 committed), Ready to qualify (5 of 5 in feed), New or changed (2 since last sweep). Each is a one-click route into the exact queue it names.
Attention strip: title, count, denominator, and a plain-language caption on every card.

Stage 1 — Scan the feed & triage "Which one do I open first?"

⚠ As-is · Deployed build
GoalPick the highest-value item to work next; clear out anything that isn't worth qualifying.
What happensA table, default-sorted by confidencePct descending. Rows show sub-category, country, lever, spend, addressable, vendor count, confidence, savings range. Decisions (park/reject) happen one row at a time, inside the Qualify panel.
  • SEV 4 Default sort is confidence-only — pulled live data confirms OPP-003/005 (76% conf, ~$267–331K) rank above OPP-001 (71% conf, $339K — the largest pocket in the feed). The CM works top-down and triages the smaller opportunity first, purely because size is invisible to the ranking.
  • SEV 3 The feed's own narrative claims "Ranked by evidence strength" — that sentence doesn't match the actual sort key, so the CM is told a rule that isn't the rule being applied.
  • SEV 3 No bulk triage. Parking or rejecting five similar tail items means opening five modals, five times through the same dialog.
  • SEV 3 No new/changed signal at row level — a CM returning after a week can't tell what's different without re-reading every row.
  • Every row repeats an "upper bound" implication with no shared explanation of why — a CM has to already know the methodology to know it's not a firm number.
✓ To-be · Prototype v2.1
GoalSame.
What happensSort is declared and defaults to Impact = addressable × confidence (an explicit control, not silent). Rows group by sub-category with a Σ-addressable subtotal per group. New/Changed chips sit on the row. Checkboxes enable a sticky bulk bar (Park…/Reject…, one shared dialog, reason still required per the product's own rule). One shared note above the table explains the upper-bound caveat once, with a "why?" link, instead of a chip on every row.
Declared "Ranked by: Impact" control; grouped rows; one upper-bound note, not a chip storm.

Stage 2 — Open & qualify "Do I trust this number enough to act on it?"

⚠ As-is · Deployed build
GoalUnderstand the play, verify the math, decide if it's real.
What happensA well-built modal: Mercer summary + 4 tiles, a recommendation band, data caveats, vendor roster (correctly labeled "Share of pocket"), functional fit, savings derivation, surfacing history. Confidence renders as a raw percentage with no ceiling.
  • SEV 4 WhatDroveThisCard — the three-factor confidence breakdown (fit × fragmentation multiplier) — exists fully built in the codebase but is never imported into the Qualify panel. A CM sees a bare "76%" with zero way to see what produced it.
  • SEV 4 Confidence has no display ceiling and no band word. Nothing stops a future well-evidenced category from showing "100%" next to an upper-bound caveat — the exact contradiction the original screenshot audit flagged, now unguarded in the actual component.
  • SEV 3 Two Approve buttons exist on one modal (the recommendation band and the footer) with no visible precedence rule.
  • SEV 3 "Terms vs benchmark" prints a hardcoded "no payment-terms data" sentence for every opportunity — even ones whose roster includes vendors that DO have terms on file (confirmed against the vendor data). The methodology-honesty pattern the product is built on is undercut by its own static copy.
  • Confidence math, when it exists in a future build, is buried below the roster and derivation rather than up front where the trust question is actually being asked.
✓ To-be · Prototype v2.1
GoalSame.
What happensConfidence is capped at 99%, always shown with a band word (High/Medium/Directional), and an ⓘ opens the exact formula + live parameters. "What drove this · confidence math" is a real, visible card between the caveat and the roster — visible for every opportunity, including the analyst-adjusted ones where the sweep formula and the final number differ. One Approve, in the footer, always in the same position; the recommendation band only holds "Add context" and "Override figures." Terms vs benchmark is computed from whichever roster vendors actually have terms on file, and stages honestly only the remainder.
Confidence math card wired into the flow; banded/capped confidence; single Approve in the footer.

Stage 3 — Decide "Approve, park, or reject — and can I change my mind?"

⚠ As-is · Deployed build
GoalMake a defensible decision and move on.
What happensReject requires a reason (good). Park requires a revisit trigger — date or condition (good). Approve is blocked while an override or unsaved input is pending (good guardrail). Once parked, the panel re-opens read-only with only "Return to feed" available.
  • SEV 3 Parking is a dead end: if the CM changes their mind and wants to approve or reject a parked item, they must first return it to the feed, then reopen it, then decide — a two-step round trip for what should be a one-click change of mind.
What's already right here
  • Reason/trigger requirements are real, not decorative — confirmed in the dialog code.
  • Approve genuinely blocks on unsaved state, preventing a stray click from committing half-finished figures.
✓ To-be · Prototype v2.1
GoalSame.
What happensSame reason/trigger requirements, same approve guardrails — plus: opening a Parked item's panel shows Reject / Return to feed / Approve together in the footer. A change of mind is one click, not a three-step round trip.
Small fix, real friction removed. This was a one-line footer change once identified — the kind of thing that's invisible until you actually try to change your mind on a parked item.

Stage 4 — Act: run the play "Turn the decision into supplier-facing work"

⚠ As-is · Deployed build
GoalPick an approach, work the checklist, produce outreach/RFP material, commit a number.
What happensA genuinely strong workspace: Mercer-recommended playbook, a persisted task checklist, one-shot draft generation (real vendor names and figures, not lorem ipsum), and a commit step.
  • SEV 3 The checklist is entirely manual — there's no way to attach a quote, a contract excerpt, or a supplier note and have anything happen with it. Whatever the CM learns while working the play stays in their head or an external email; the draft never updates.
  • SEV 3 Drafts are one-shot: click "Supplier outreach," get one version of the text, edit it in place. There's no history — if the CM's edit turns out wrong, or a colleague overwrites it, the original Mercer draft is gone.
  • SEV 4 "Commit value" has no validation — timing and basis are optional selects. A CM can book a number into the committed pipeline with no stated basis for it, which undercuts the exact auditability the commit step exists to provide.
✓ To-be · Prototype v2.1
GoalSame.
What happensAn "Evidence & context" block sits above the drafts: attach a document or paste a note → Mercer analyzes it, saves the insight to the play, and re-issues every existing draft as a new version with the evidence folded in. Every draft is versioned (v1 Mercer-generated, v2 "folded in [evidence]", v3 "manual edit" …) — all selectable, none overwritten. Timing and basis are both required before "Commit value" enables.
Evidence in → Mercer analyzes → drafts re-issue as a new version, never overwriting an edit.

Stage 5 — Commit & hand off "Where does this go now?"

⚠ As-is · Deployed build
GoalConfirm the commitment landed and know where to track it.
What happensA toast reads "{id} committed — tracking in Value Realization." It is plain text — there's no click-through. The CM either remembers to navigate to Value Realization themselves or loses the thread.
  • SEV 2 The exact moment the CM would most want a forward link — right after committing a number — is a dead-end toast.
✓ To-be · Prototype v2.1
GoalSame.
What happensSame toast text, but "Track in Value Realization" renders as a clickable link inside it that jumps straight to the committed play's tracking panel.

PART 04

What v2.1 Already Resolves — and What It Doesn't

✓ Genuinely demonstrated
  • Declared, size-aware ranking (Impact) replacing a silent confidence-only sort
  • Confidence trust chain: banded, capped, with the math visible on demand
  • Bulk triage with the same reason/trigger rules the single-row flow already enforced
  • Change-of-mind path out of Parked without a round trip
  • Evidence-in → analysis → versioned-draft loop for Act
  • Required commit basis, closing the auditability gap
  • Restyled onto the real @navanta-ai/design-system tokens (not an approximation)
⚠ Still open / not this document's job
  • "Mercer analyzes your evidence" is a keyword heuristic in the prototype, not a real model call — the UX pattern is validated, the AI behavior behind it is not.
  • File attachment in the prototype accepts a filename only — no real upload, storage, or retrieval design yet.
  • No altitude scope switcher (Plant/Region/Enterprise-BU) — both journeys are stuck at category scope.
  • No exec/CPO read-only rollup path — this audit is CM-only, by design, since that's the flow in scope.
  • Grouped-by-sub-category feed view hasn't been tested against a much larger feed (hundreds of rows) — the pattern may need pagination-per-group or virtualization at scale.
PART 05

Open Questions for the Next Design Pass

These are the decisions this audit surfaces but doesn't make. Worth resolving before more prototype iteration.

1 · Is Impact (addressable × confidence) the right default ranking, or a placeholder?
The prototype uses it as a declared, honest stand-in until the engine exposes true Prize × Feasibility × Provability² per pocket. Do we ship the proxy now, or wait?
2 · How real does "Mercer analyzes your evidence" need to be for a v1?
Keyword-heuristic (cheap, deterministic, ships fast) vs. an actual grounded LLM call against the uploaded document (the real value proposition, more integration work). This changes the Act screen's build estimate significantly.
3 · What's the real document-storage story?
Uploaded quotes/contracts need to land somewhere real (S3-equivalent, linked to the opportunity record) before "attach a document" is more than a filename in the prototype.
4 · Does grouped-by-sub-category hold up at real scale?
Five opportunities in five groups reads clean. What does it look like at 80 opportunities across 15 sub-categories — collapsed groups by default? A count threshold before grouping kicks in?
5 · Bulk triage — reject reasons per-item or one shared reason for the whole batch?
The prototype applies one reason to the whole selection (matches the existing single-reason dialog). Is that acceptable, or does compliance need a reason per opportunity even in bulk?
6 · Where does the "return a parked item to feed" affordance still matter, if approve/reject now happens directly from Parked?
Keep both paths, or is "Return to feed" now just for genuine re-triage (not a decision)?
7 · Priority order for what actually ships first.
Given the SEV-4/SEV-3 register in Part 3 — is the build sequence: (a) confidence trust chain, (b) declared ranking, (c) bulk triage, (d) evidence loop — or does the team see it differently?
